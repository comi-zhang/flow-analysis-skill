# 个人流水分析

把多渠道对账单（银行 PDF/CSV、支付宝、微信）整理成**能对账的收支口径**，并识别数据质量问题。

难点不在算总数，而在三件事：**同一笔被记两次**、**资金搬运被当成消费**、**来源数据本身有错**。
下面按这三件事组织。

## 先问清三件事，否则结论一定错

在动手前确认，缺一个就会得出错误结论：

1. **输入是什么**：哪些渠道、什么格式（PDF / CSV / Excel）、有没有导出原始文件。
2. **口径怎么定**：哪些算消费、哪些算资金搬运（见 [references/caliber.md](references/caliber.md)）。
   尤其要问：**人情往来（给家人转账）算不算消费？** 这一个选择能让结果差 50% 以上。
3. **有没有"只有你知道"的事实**：报销、押金、代付、借出。这些数据里看不出来，
   但会显著影响结论。先问，再分析。

## 工作流

### 1. 读取即掩码

**在任何落库、落盘、进日志之前完成掩码**——这是唯一有效的时点，事后清理必漏。

```bash
python scripts/mask_pii.py --input-dir raw/ --output-dir masked/ \
  --owner-names '真实姓名,常用别名' --mode encode
```

- 账单人本人 → 固定代称（如「张三」）
- 其他自然人 → 确定性假名，**同一人恒定同码**（保住跨表 JOIN 能力）
- 银行卡/手机号/订单号/学号 → 稳定编码（`C-` / `M-` / `T-` / `S-`），**不要用 `****`**

为什么用编码而不是 `****`：掩码会丢掉「是不是同一张卡」这个事实，而配对规则要靠它比对。

**要处理 `raw_line`（原始行留底）**——它是最容易漏的一处，留底不能留真值。

### 2. PDF 对账单：先探结构再解析

PDF 是链路里最脏的输入，**先跑探针再写解析器**：

```bash
python scripts/pdf_probe.py --pdf 交易流水.pdf --pages 8
```

探针给出三个决定性的数：金额行/日期行比值（能否按行尾切）、折行卡号片段数
（账户列是否可信）、每页重复的表头行。要点：

- **不要用"8 位数字开头"判断日期**：折行的卡号尾段也是 8 位（形如 `07639999`），
  必须再校验月/日范围。
- **模板行阈值要严**：折行后的字段残片会长得像模板（实测「技有限公司 财付通扣款」每页都有），
  用 ≥90% 页面或行号区间剔除。
- **PDF 优先索取 CSV/Excel**：同一家银行通常有结构化导出，结构性差距很大。

完整方法（含真实观测数据）见 [references/pdf-statement.md](references/pdf-statement.md)。

### 3. 导出的分页陷阱

从飞书多维表格导出记录时，**不要用 `has_more` + `page_token` 循环**：接口可能返回
`has_more=true` 却不给 `page_token`，循环会死转（在定时任务里等于静默卡死）。
改用 `--offset` 分页，并加页数安全阀。细节见 [references/feishu-base.md](references/feishu-base.md)。

### 4. 数据质检（**最容易跳过、但最该做**）

```bash
python scripts/qa_flow.py --input-dir masked/ --report qa.md
```

四项检查，每一项都对应一类真实事故：

| 检查 | 能发现什么 |
| --- | --- |
| **余额链闭合** | 金额/行数是否有错（见下，**判据与顺序无关、按来源整体判定**） |
| **时间精度** | 只有日期的记录（PDF 常见）会被补成 `00:00`，**不能参与"凌晨/时段"类规则** |
| **跨渠道重复** | 同一笔在平台和银行各记一次（绑卡支付必然如此） |
| **退款未对冲** | 摘要写着「已退款」但退款腿没配上对，整笔仍计入消费 |

**余额链是最有价值的单项检查**：它同时验证"金额对不对"和"有没有解析错位"。
但它有三个必须避开的方法陷阱——**这三个都真实踩过，前两个曾让我得出完全错误的结论**：

1. **不能用"相邻两笔相减"**。它要求「记录顺序 = 真实发生顺序」，而导出的行序
   并不保证如此（来源只有日期时日内顺序也不可知）。实测同一份数据：按顺序比只有
   **49.6%** 自洽，改成与顺序无关的判定后是 **100%**——差点判定这家银行金额只有一半可信。

   正确判据（与顺序无关）：对每笔交易，检查它的**前序余额是否存在**于同组余额中。

   ```
   支出：前序余额 = 本笔余额 + 金额
   收入：前序余额 = 本笔余额 − 金额
   ```

2. **不能按"账户/卡号"分组**。同一来源里的多个卡号可能是**同一个余额主体**
   （同一账户多卡），卡号列本身也可能来自 PDF 折行而不可信。实测按卡号分组有
   **18 处断裂**，按来源合并后是 **0 处**。脚本会同时报告两个数，来源级正常而
   账户级异常时标记「账户列可疑」。
3. **健康值不是 100%**。账期首笔的前序余额发生在账期之前，天然找不到，所以**链闭合
   的来源恰好有 1 笔未匹配**。判据是「未匹配 ≤ 1」，不是「自洽率 = 100%」；
   自洽率天然接近 `1 − 1/笔数`，笔数少时偏低属正常。

修正后的实测结果：18 个来源**全部链闭合**（0 处断裂），说明金额与行数都可信——
之前"某银行只有 5%/49.6% 自洽"的说法是方法错误造成的假象。

### 5. 跨渠道去重

判定「同一笔双边记账」需要**同时满足四条**：

1. 金额一致（±0.01）
2. 同一天
3. **支付时间相近**（两侧都有精确时间时 ≤120 分钟；任一侧是「仅日期」则退化为同日）
4. 对手名归一后相同或互相包含（去空格括号、去「股份有限公司」等后缀）

第 4 条不能省：实测存在「同额同日但确实是两笔」的情况。
配对必须**双侧占用**（一笔只能被占用一次）——这是最容易写错、也最容易产生假配对的地方。

### 6. 口径重算

```bash
python scripts/caliber_report.py --input-dir masked/ --out-dir reports/
```

两个口径的定义与修正规则见 [references/caliber.md](references/caliber.md)：

- **真实支出** = 账户真实流出（排除内部划转、重复记账、交易未成功、清算过渡、已确认退款对冲）
- **真实消费** = 真实支出再剔除「资金搬运」（理财申赎、账户间划转、人情往来）

**别只报一个数**。差额本身就是结论：实测一位用户的真实支出里只有 22% 是消费，
其余 78% 是理财申赎和账户互转。用户看到"支出 118 万"会以为自己在乱花钱，
实际消费只有 26 万。

### 7. 修正虚高（四类）

算出消费后，再扫一遍这四类——它们会让消费**虚高**：

| 类型 | 识别方式 |
| --- | --- |
| 退款未对冲 | 摘要含「已全额退款」/「已退款(¥X)」但退款腿未配对 |
| 银行计息混入 | 对手/摘要含「应付利息」「结息」——这是银行给你计息，不是消费 |
| 跨渠道重复 | 见步骤 5 |
| 已报销支出 | 支出后短期内他人汇入等额款项（需要问用户） |

同时修正**分类错误**：例如学校「代收扣款」常被归到餐饮，实际是学费+住宿费。
分类错误不影响总额，但会让大类结构失真。

### 8. 输出

- **看板优先于表格**：用户说"看大盘"时要的是 dashboard。飞书多维表格的图表组件
  `group_by` 支持**两个维度**，正好做「年 × 大类」堆叠图；一个维度做趋势/占比。
- 看板上写清**口径说明**（文本组件），否则数字离开上下文就失去意义。
- 中间分析产物落盘时用**编码后**的数据，原始文件用完即删（或移到仓库外的私密目录）。

## 已知的数据坑（按杀伤力排序）

1. **余额链校验的三个方法陷阱**：①用"相邻两笔相减"（导出会丢行序）；②按"账户/卡号"分组
   （同账户多卡 + 卡号列折行不可信）；③把"自洽率 100%"当健康值（账期首笔天然对不上）。
   三个都会得出**完全错误**的结论。判据见步骤 4。
2. **PDF 单元格串行**：文字抽取时列边界丢失，相邻单元格的残余字符粘到对手名上
   （如「司 C-XXXX 某某公司」——`司` 是上一行「…有限公司」的尾巴）。
   实测把「朝朝宝转入（基金）」的对手名配成「拼多多」：**金额/方向/余额都对，只有对手名错**。
   **金额通常仍可信**（余额链能证明），但**对手名不可信**，不能拿它做匹配主键。
3. **PDF 折行 + 8 位数字**：卡号尾段也是 8 位数字（形如 `07639999`），
   用正则 `^\d{8}` 判日期会把卡号当日期；折行残片还会伪装成"每页重复的表头"被误删。
4. **伪凌晨**：日期型记录补成 `00:00` 后被归入"凌晨"，让时段类规则全部误报。
   实测某数据集 22% 的记录是这种。**做时段分析前必须先查时间精度**。
5. **退款沿用原单号**：用「渠道交易单号」做去重锚点会把原支付和退款折叠成一行。
   用来源系统自己的稳定主键（如飞书 `record_id`）才安全。
6. **对手名里的账号**：银行把「账号 + 对手名」挤在同一字段，同一个账号可能配不同对手名。

## 交付前的自检

- [ ] 掩码在读取阶段完成，`raw_line` 也处理了
- [ ] PDF 来源跑过 `pdf_probe.py`，折行/模板剔除策略已确认
- [ ] 余额链**按来源**判定且**未匹配 ≤ 1**（不是看自洽率）；`账户列可疑` 的来源未用于账户维度分析
- [ ] 时间精度分布已统计，时段类结论已排除日期型记录
- [ ] 跨渠道重复用四条判据，且双侧占用
- [ ] 消费口径明确写出剔除了什么，以及"人情往来"的处理方式
- [ ] 四类虚高都扫过，金额差异有记录
- [ ] 产物中不含未掩码的个人信息（跑 `scripts/mask_pii.py --audit-only` 复核）
- [ ] 原始 PDF/对账单未入库（`*.pdf` 已在 `.gitignore`）
